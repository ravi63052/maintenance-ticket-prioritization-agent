# Renewable-Energy Maintenance Ticket Prioritization

A runnable case-study prototype that classifies maintenance tickets, estimates severity, suggests a probable root cause and next action, and routes the ticket to an operational team.

> **Important scope note:** The supplied CSV contains only six dummy examples. This project deliberately does not claim to train or validate a production supervised ML classifier from six rows. It uses a small NLP retrieval layer (TF-IDF + cosine similarity) over the bundled examples, an explainable keyword taxonomy, transparent weighted severity rules, and deterministic routing/recommendation tools. The result is a simple agent-style workflow, not an autonomous LLM agent.

## Features

- FastAPI backend with interactive API documentation at `/docs`.
- HTML/CSS/JavaScript frontend served by the same Python process.
- Ticket category classification with evidence and confidence estimate.
- TF-IDF retrieval of similar bundled tickets.
- Severity score from 0–100 with component breakdown and safety override.
- Probable root-cause hypothesis with an explicit uncertainty note.
- Category-specific recommended next action.
- Rule-based team and queue routing with an agent execution trace.
- Bundled sample-ticket workflow, API health check, and evaluation endpoint.
- Railway deployment configuration and automated tests.

## Run locally (Windows PowerShell)

Python 3.10+ is recommended.

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
uvicorn backend.app:app --reload
```

Open `http://127.0.0.1:8000` for the UI and `http://127.0.0.1:8000/docs` for the API docs.

Linux/macOS activation:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.app:app --reload
```

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Health check (also used by Railway) |
| GET | `/api/demo` | Dataset and capability summary |
| GET | `/api/tickets` | Return bundled sample tickets |
| POST | `/api/analyze` | Analyze a user-supplied ticket |
| POST | `/api/run` | Alias for `/api/analyze` |
| POST | `/api/analyze-sample/{ticket_id}` | Analyze a bundled ticket, e.g. `T002` |
| GET | `/api/metrics` | In-sample diagnostic metrics, clearly labelled |
| GET | `/docs` | Swagger/OpenAPI documentation |

Example request:

```bash
curl -X POST http://127.0.0.1:8000/api/analyze \
  -H "Content-Type: application/json" \
  -d '{"description":"Gearbox vibration has increased with abnormal noise on turbine WTG-12","asset_type":"wind","ticket_id":"NEW-101","generation_impact":"high"}'
```

Optional structured fields are `downtime_hours`, `generation_impact` (`low`, `medium`, `high`) and `people_at_risk`.

## How the workflow works

1. **Validate input:** FastAPI/Pydantic checks the request fields and bounds.
2. **Retrieve context:** TF-IDF transforms the description and cosine similarity retrieves the nearest bundled ticket examples. Retrieved rows are evidence, not external truth.
3. **Classify:** An explainable keyword taxonomy chooses a maintenance category. If no category keyword matches, a sufficiently similar bundled example may be used; otherwise the system uses a safe general-maintenance fallback.
4. **Score severity:** A 0–100 score combines safety risk (25%), generation impact (30%), equipment condition (25%) and urgency (20%). An explicit safety-risk signal invokes a critical-priority override.
5. **Suggest a root cause:** Category-specific text patterns produce a *probable* hypothesis. It is never presented as a confirmed diagnosis.
6. **Recommend an action:** A category-specific playbook selects an action. Critical recommendations are visibly prefixed.
7. **Route:** The routing tool assigns a team and queue. Safety risk takes precedence and routes to Site Safety while notifying the relevant maintenance team.
8. **Return trace:** The API returns the intermediate steps, retrieval evidence, score components and limitations so the decision can be inspected.

## Severity scoring assumptions

Each component is rated from 0 to 100 and combined as:

`score = 0.25*safety + 0.30*generation_impact + 0.25*equipment_condition + 0.20*urgency`

| Score | Label |
|---:|---|
| 80–100 | Critical |
| 60–79 | High |
| 35–59 | Medium |
| 0–34 | Low |

An explicit safety hazard or `people_at_risk=true` forces the score to at least 90. These weights, signals and thresholds are prototype assumptions and must be reviewed by Greenko operations, safety and maintenance specialists before real use.

## Evaluation and tests

Run unit tests:

```bash
python -m unittest discover -s tests -v
```

Generate the diagnostic report:

```bash
python scripts/evaluate.py
```

The report is saved to `docs/evaluation_results.json`. It compares the rules' outputs with the six supplied target labels. **This is an in-sample diagnostic only**, not an independent test result: the dataset is tiny, synthetic and does not support a credible generalization claim. The severity labels are also target labels from the bundled examples, while the scoring weights are hand-designed assumptions.

## Railway deployment

1. Push the complete project to a GitHub repository (do not commit `.env`, credentials or virtual environments).
2. Sign in to Railway and create a new project from that GitHub repository.
3. Railway detects the Python dependencies in `requirements.txt`; `railway.json` supplies the start command and `/api/health` health check. The existing `Procfile` provides the same start command as a fallback.
4. In Railway, generate a public domain for the service.
5. Wait for deployment to finish, then open the public URL and verify `/api/health`, the UI, and a sample analysis.
6. Record the deployed URL in your submission notes. A deployment is not complete until this live verification succeeds.

No external API key is needed for the current implementation. If an LLM provider is added later, store its key as a Railway environment variable, never in source control.

## Limitations and production-readiness gaps

- Six examples are not enough for supervised model training, reliable test metrics, or broad asset coverage.
- TF-IDF similarity is lexical; it does not understand deep semantic equivalence and may retrieve a superficially similar ticket.
- Keyword classification can miss synonyms, abbreviations, spelling errors and multi-issue tickets.
- Severity weights and routing policies are illustrative and require domain-expert approval.
- Root-cause suggestions are hypotheses based on text, not fault diagnosis from SCADA, historian, inspection or sensor data.
- No LLM, RAG over documents, external tools, authentication, ticket database, audit store, or human approval workflow is included. The agent-style component is a deterministic sequence of local tools/rules.
- Before production: collect expert-labelled historical tickets; define asset/site-specific policies; use site-held-out or time-aware evaluation; monitor drift; add access control, audit logging, observability, retries, human approval and integration with CMMS/SCADA systems.
